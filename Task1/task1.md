## Описание диаграммы контейнеров

* Портал витрины данных (Self-Service BI Portal) — основной интерфейс для сотрудников. Тут строятся отчёты, дашборды,
  конструкторы.
* Слой аналитических данных (Data Lakehouse) — хранение очищенных и агрегированных данных (без медицинских карт). Делится на домены (финансы, персонал, инвентаризация и т.д.).
* Слой интеграции (Data Mesh / API / Kafka) — получение данных из разных бизнесов (клиники, банк, ИИ, фармацевтика, электроника).
* ИИ-сервисы — подключаются к данным, где это разрешено, обрабатывают медицинскую информацию.
* Финтех-сервисы — банк и финтех-продукты, подключённые к общему ландшафту через слой интеграции.
* Legacy DWH (SQL Server 2008 + Power Builder) — временно остаётся, но постепенно заменяется.

## Проблемные места

1. Старый DWH тормозит — отчёты строятся часами.
2. Нет гибкости — сложно быстро подключать новые бизнесы (каждый раз нужно дописывать кучу логики).
3. Дублирование логики — одни и те же бизнес-правила реализованы в разных местах.
4. Сложность масштабирования — нагрузка растёт, а архитектура не тянет.
5. Зависимость от устаревших технологий — Power Builder и SQL Server 2008 тормозят развитие.

## Приоритизация (метод MoSCoW)

* Must (обязательно):
    * Построить новый слой аналитических данных (Data Lake + DWH).
    * Создать витрину данных для самообслуживания.
    * Организовать интеграционный слой для новых бизнесов.
* Should (желательно):
    * Снизить зависимость от Legacy DWH.
    * Централизовать бизнес-правила (убрать дубли).
* Could (можно, если останется время):
    * Внедрить продвинутую автоматизацию data governance.
    * Добавить умные рекомендательные отчёты.
* Won’t (пока не будем):
    * Полностью отказаться от легаси в первый год (слишком рискованно).
